A. The Persistent Tail Buffer Context (Lines 113–138)

Recall our discussion from Lesson 3 about the 0.73% boundary loss problem. Here is how Zig stores the trailing 480 bytes between GenStage chunks: 

pub const DspData = struct {
    overlap_buf: [480]u8,
    overlap_len: usize,
    samples_processed: u64,
    preambles_detected: u64,
    crc_valid: u64,
    single_bit_recovered: u64,
};

pub const DspContext = beam.Resource(*DspData, @import("root"), .{});

By defining DspContext as a beam.Resource, the Erlang VM automatically manages its lifecycle, garbage collecting the native memory only when the Elixir process terminates.

B. SIMD Magnitude Vectorization (Lines 186–207)

Here is the exact 16-lane SIMD loop we studied in Lesson 2: 

const simd_lanes = 16;
while (s_idx <= simd_limit) : (s_idx += simd_lanes) {
    var i_vec: @Vector(simd_lanes, f32) = undefined;
    var q_vec: @Vector(simd_lanes, f32) = undefined;

    inline for (0..simd_lanes) |lane| {
        const byte_pos = (s_idx + lane) * 2;
        i_vec[lane] = @as(f32, @floatFromInt(iq_buf[byte_pos])) - 127.5;
        q_vec[lane] = @as(f32, @floatFromInt(iq_buf[byte_pos + 1])) - 127.5;
    }

    const mag2 = i_vec * i_vec + q_vec * q_vec;
    const mag = @sqrt(mag2);

    inline for (0..simd_lanes) |lane| {
        mag_buf[s_idx + lane] = mag[lane];
    }
}

C. $O(1)$ Syndrome Error Recovery (Lines 239–256)

When a frame fails CRC-24, notice how Zig looks up the 24-bit remainder against the precomputed table: 

while (bit_pos < 112) : (bit_pos += 1) {
    if (SYNDROME_TABLE[bit_pos] == syndrome) {
        // Found the exact corrupted bit: flip it in place!
        candidate_frame[bit_pos / 8] ^= (@as(u8, 1) << @intCast(7 - (bit_pos % 8)));
        ctx.single_bit_recovered += 1;
        frames[num_frames] = candidate_frame;
        num_frames += 1;
        recovered = true;
        break;
    }
}

2. The Streaming Pipeline (lib/sdr_scout/pipeline/)

Open lib/sdr_scout/pipeline/detector_consumer.ex.

The Demand Contract
def init(opts) do
  ...
  {:consumer, %{ctx: ctx, airspace: airspace},
   subscribe_to: [{producer, max_demand: 4, min_demand: 1}]}
end

Notice max_demand: 4, min_demand: 1! The consumer only asks for up to 4 chunks (256 KB) at a time. If Zig is busy processing, the producer pauses emission. Memory usage is strictly bounded—no unbounded queues, no OOM killer.

Checking Your Mastery

1. Why is DspContext defined as a beam.Resource rather than an ordinary raw C memory pointer?
  • Raw C pointers cannot be dereferenced by SIMD vector instructions on modern x86 chips.
  • BEAM resources track lifecycle and automatically free native memory when Elixir processes terminate.
  • Erlang GenStage requires all producer subscriptions to be serialized into JSON format strings.
  • The Zig compiler rejects functions that accept mutable pointers to struct array memory buffers.
Correct! A `beam.Resource` ties the lifecycle of native C/Zig heap memory to an Erlang reference. When the holding Elixir process dies or the reference is garbage collected, the BEAM calls the resource destructor, preventing memory leaks.
2. In DetectorConsumer, why does setting max_demand to 4 prevent out-of-memory (OOM) failures under heavy load?
  • It restricts the radio hardware antenna to receiving signals from no more than four airplanes.
  • It forces the operating system kernel to limit physical DRAM memory allocation to four megabytes.
  • The consumer only requests four chunks at a time, preventing upstream producers from filling queues.
  • Setting demand above four causes the Zig SIMD vector loop to trigger division by zero faults.
Correct! In GenStage's pull model, the upstream producer cannot emit chunks until the consumer explicitly requests them. Restricting demand to 4 chunks ensures there are never more than 256 KB of in-flight buffers, making buffer bloat and OOM crashes impossible.
