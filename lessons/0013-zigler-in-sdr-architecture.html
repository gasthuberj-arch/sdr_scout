Zigler in SDR Scout: Mechanics, Memory Models, and SIMD Seams

When engineers build Software-Defined Radio receivers, they almost universally face a binary dilemma:

  • Choose C++ / Rust / GNU Radio: You get raw SIMD speed and cache-line control, but you inherit thread orchestration headaches, pipeline deadlocks, manual buffer sizing, and fragile crash semantics (a single segfault drops the whole daemon).
  • Choose a High-Level Dynamic Language: You get actor concurrency and robust networking, but you drown in garbage collection pauses, boxed object overhead, and zero SIMD vectorization.

Zigler eliminates this dilemma by embedding the Zig systems language directly into Elixir. In SdrScout, we use Zigler to achieve a clean, high-performance seam: Elixir manages the system; Zig crunches the spectrum.

1. What Zigler Actually Does Under the Hood

In lib/sdr_scout/native/dsp.ex, you see the declaration: 

defmodule SdrScout.Native.Dsp do
  use Zig,
    otp_app: :sdr_scout,
    resources: [:DspContext]

  ~Z"""
  const std = @import("std");
  const beam = @import("beam");

  pub fn process_chunk(res: DspContext, chunk: []const u8) beam.term {
      ...
  }
  """
end

When mix compile runs, Zigler executes a multi-step compilation pipeline:

  1. AST Extraction: Zigler extracts the code inside the ~Z""" sigil and inspects its exported functions, arguments, and return types.
  2. C/BEAM Wrapper Synthesis: It automatically generates an Erlang NIF wrapper layer (module.zig) that interfaces with the Erlang Run-Time System (ERTS) C headers (erl_nif.h). It handles all enif_get_resource, enif_inspect_binary, and enif_make_list_cell boilerplate.
  3. Standalone Zig Compilation: It invokes the local Zig toolchain (managed via mix zig.get) using zig build, outputting a native shared library (Elixir.SdrScout.Native.Dsp.so) into _build/<env>/lib/sdr_scout/priv/lib/.
  4. Elixir Binding Generation: In the compiled Elixir module, it generates stub functions with the exact same arity that invoke :erlang.load_nif/2.
Why Zigler Beats Traditional C/Rustler NIFs

In pure C NIFs, a single mismatched pointer or forgotten enif_release_resource crashes the BEAM VM. In Rustler, you must install Cargo, manage heavy external build targets, and fight the borrow checker on contiguous ring buffers. Zigler gives you explicit memory allocators, standalone toolchains without external runtime dependencies, and native @Vector SIMD primitives directly in your Elixir source tree.

2. Zero-Copy Binary Semantics: The 64-Byte Rule

In SDR pipelines, passing raw I/Q samples across foreign function boundaries can easily destroy throughput if data is copied between heaps.

How does Zigler avoid this? The BEAM classifies binaries into two memory representations:

  • Heap Binaries (≤ 64 bytes): Allocated directly inside the Erlang process's private memory heap. Moving them requires copying.
  • Refc (Reference-Counted) Binaries (> 64 bytes): Allocated in shared global off-heap memory. Processes only pass around a tiny 24-byte ProcBin descriptor pointing to the shared buffer.

Because our SDR chunks are 65,536 bytes (64 KB), the BEAM treats them as Refc binaries. When Elixir calls Dsp.process_chunk(ctx, chunk), Zigler passes a pointer to the existing shared memory buffer: 

// chunk is a native Zig slice ([]const u8) pointing directly into the BEAM refc binary!
pub fn process_chunk(res: DspContext, chunk: []const u8) beam.term

There is zero memory allocation and zero copying to get the raw 64 KB radio samples from the Elixir GenStage pipeline into the native Zig CPU registers!

3. The Stateful Memory Model: beam.Resource

Software-Defined Radio is inherently stateful. You cannot process 64 KB chunks as isolated stateless blocks because signals straddle chunk boundaries:

An ADS-B Mode-S message spans 240 complex samples (480 bytes at 2.0 MSPS). If a transmission begins at byte 65,400 of Chunk $N$, its tail lands in Chunk $N+1$. A stateless NIF would drop it every time (causing a ~0.73% packet loss rate).

To solve this, Zigler allows us to declare an Erlang Resource struct: 

pub const DspData = struct {
    overlap_buf: [480]u8,
    overlap_len: usize,
    samples_processed: u64,
    preambles_detected: u64,
    crc_valid: u64,
    single_bit_recovered: u64,
};

pub const DspContext = beam.Resource(*DspData, @import("root"), .{});

Here is how the memory lifecycle works:

  1. When Dsp.new_context() is invoked, Zig calls beam.allocator.create(DspData).
  2. The BEAM wraps this pointer inside an opaque #Reference<...> term returned to Elixir.
  3. The Elixir DetectorConsumer GenStage process holds this reference in its state.
  4. When subsequent chunks arrive, the reference is passed back to Zig, which unpacks the persistent struct in $\mathcal{O}(1)$ time.
  5. Garbage Collection & Safety: If the Elixir consumer process crashes or restarts, the BEAM Garbage Collector automatically calls the resource destructor, freeing the native memory without leaks or dangling pointers.

4. SIMD Linear Magnitude: @Vector(16, f32)

The raw RTL-SDR delivers interleaved unsigned 8-bit complex samples: $[I_0, Q_0, I_1, Q_1, \dots]$. To detect pulses, we must compute the envelope magnitude:

$$|z[n]| = \sqrt{(I[n] - 127.5)^2 + (Q[n] - 127.5)^2}$$

In scalar C or Elixir, computing 32,768 square roots per chunk would consume tens of thousands of CPU cycles. In Zig, we process 16 samples simultaneously using target-independent LLVM vectors: 

// 16 lanes of 32-bit floating point numbers
const Vec16 = @Vector(16, f32);

var v_i: Vec16 = undefined;
var v_q: Vec16 = undefined;

// Fill vector registers from normalized byte pairs
var lane: usize = 0;
while (lane < 16) : (lane += 1) {
    v_i[lane] = @as(f32, @floatFromInt(iq_buf[sample_idx * 2])) - 127.5;
    v_q[lane] = @as(f32, @floatFromInt(iq_buf[sample_idx * 2 + 1])) - 127.5;
}

// SIMD parallel squaring, addition, and vector square-root!
const mag_sq = (v_i * v_i) + (v_q * v_q);
const mag_vec = @sqrt(mag_sq);

On an x86_64 CPU with AVX2, LLVM lowers this directly to vmovups, vfmadd, and vrsqrtps / vsqrtps instructions inside the 256-bit ymm registers. On ARM64 (Apple Silicon or Raspberry Pi 4/5), it maps directly to 128-bit NEON vector registers.

5. In-Zig CRC-24 Syndrome Repair

ADS-B frames protect their 112-bit payloads using a 24-bit cyclic redundancy check with polynomial $0x1FFF409$.

Instead of passing unverified pulse candidates up to Elixir, Zigler performs complete frame validation and single-bit error recovery in native memory:

  1. At boot, Zig computes a 112-entry syndrome table (SYNDROME_TABLE[112]), mapping every single-bit position $0 \dots 111$ to its expected remainder.
  2. When a candidate frame is sliced, Zig computes its 24-bit CRC remainder.
  3. If rem == 0, the frame is pristine.
  4. If rem != 0, Zig searches SYNDROME_TABLE: if it matches bit position $k$, Zig executes: 
    frame[k / 8] ^= @as(u8, 1) << @intCast(7 - (k % 8));
    The flipped bit is corrected in-place, salvaging the packet!
  5. Only frames that pass CRC (or are successfully repaired) are returned to the BEAM. All noise pulses and corrupted packets are discarded in Zig, shielding Elixir from garbage collection pressure.

6. The Golden Architectural Seam

Responsibility Layer Why It Belongs There
Buffer Slicing & Tail Stitching Zig NIF Zero-copy pointer arithmetic in contiguous C-style memory.
Vector Envelope Calculation Zig NIF @Vector(16, f32) AVX2/NEON vector instructions.
Preamble Pulse Correlation Zig NIF High-frequency inner loop checking 32,000 offsets per chunk.
CRC-24 & 1-Bit Syndrome Repair Zig NIF Bit-manipulation and table lookups before creating any Elixir terms.
GenStage Flow Control & Backpressure Elixir / OTP Dynamic demand regulation prevents buffer overruns when CPU is busy.

Terminal UI & WebSockets Elixir / OTP High-level string formatting, Phoenix LiveView, and network protocols.

Checking Your Mastery

1. Why is passing a 64 KB SDR chunk from Elixir to Zigler zero-copy?
  • Elixir serializes the binary using Erlang external term format.
  • Zigler allocates an internal C array and clones the memory.
  • Binaries over 64 bytes are refc and passed as raw pointers.
  • The Linux kernel transparently re-maps the pages via double mmap.
Correct! The BEAM stores any binary strictly larger than 64 bytes as a reference-counted (refc) binary in shared off-heap memory. When passed into a NIF, ERTS passes the raw pointer directly as a Zig slice ([]const u8) without copying.
2. What happens to the native DspContext memory if the Elixir consumer process crashes?
  • It causes an operating system memory leak until the VM restarts.
  • The BEAM GC automatically invokes the resource object destructor.
  • It triggers an immediate segfault and halts the Erlang node.
  • The OS kernel reclaims it only when the entire machine reboots.
Correct! By registering DspContext as a beam.Resource, the native memory allocation is bound to an Erlang reference term. When the process holding the reference terminates, the BEAM Garbage Collector automatically triggers the resource destructor, preventing leaks.
3. Why is CRC-24 and syndrome repair performed inside Zig rather than in Elixir?
  • Elixir does not support bitwise XOR or shift operators on binary.
  • Zigler requires all return values to be validated by the compiler.
  • It discards invalid candidate frames before creating Elixir terms.
  • CRC calculations require direct hardware access to GPU registers.
Correct! In an SDR receiver, 99.9% of candidate pulses are noise. Computing CRC-24 and syndrome error correction in Zig eliminates invalid candidates in native memory before allocating any Elixir terms or placing garbage on the BEAM heap.
