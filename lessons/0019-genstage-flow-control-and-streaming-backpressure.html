GenStage Flow Control & Streaming Backpressure in SDR Pipelines

In Software-Defined Radio (SDR), the physical world imposes an unforgiving constraint: the ADC clock never stops. Whether sampling 2.0 MSPS from an RTL-SDR or 20 MSPS from a HackRF, hardware delivers a relentless, continuous byte stream driven by quartz crystal oscillations.

In this lesson, we analyze how SdrScout reconciles the hard real-time physical clock of radio hardware with the soft real-time execution of the Erlang VM (BEAM). We dissect the demand-driven mechanics of GenStage, quantify memory and queuing limits using formal queueing models, examine zero-copy refc binary mechanics across process mailboxes, and compare BEAM actor backpressure directly with GNU Radio's virtual-memory circular buffer (vm_circbuf) architecture.

1. The Streaming Dilemma in SDR: The Inexorable Physical Clock

When receiving radio frequency signals, an Analog-to-Digital Converter (ADC) digitizes continuous physical voltages into discrete complex $I/Q$ baseband pairs at a constant sampling frequency $f_s$:

$$R_{\text{byte}} = f_s \times N_{\text{channels}} \times B_{\text{sample}}$$

For Mode-S / ADS-B reception at $f_s = 2.0\text{ MSPS}$ with 8-bit unsigned interleaved $I$ and $Q$ channels ($N_{\text{channels}} = 2$, $B_{\text{sample}} = 1\text{ byte}$):

$$R_{\text{byte}} = 2.0 \times 10^6 \text{ samples/s} \times 2 \times 1 \text{ byte} = 4{,}000{,}000 \text{ bytes/s} = 4.0\text{ MB/s}$$

In SdrScout, raw radio samples are grouped into chunks of $S_{\text{chunk}} = 65{,}536\text{ bytes}$ (64 KB), representing exactly 32,768 complex samples. The chunk duration $T_{\text{chunk}}$ is:

$$T_{\text{chunk}} = \frac{N_{\text{samples}}}{f_s} = \frac{32{,}768}{2.0 \times 10^6\text{ s}^{-1}} = 16.384\text{ ms}$$
The Fundamental Dilemma: Hard Physical Clock vs. Soft Real-Time OS

Unlike a TCP socket or disk reader where flow can be paused via TCP window advertisements or blocking I/O syscalls, an antenna cannot be paused. Electromagnetic radiation impinges on the antenna regardless of CPU load. If downstream DSP processing lags incoming throughput by even 1%, an architectural crisis occurs:

  • Unbounded Queues $\to$ Out-Of-Memory (OOM): If incoming rate $\lambda$ exceeds service rate $\mu$, queue growth is monotonic: $\frac{dQ(t)}{dt} = \lambda - \mu$. At a mere 1% deficit ($\lambda = 1.01\mu$), data accumulates at $40\text{ KB/s} = 2.4\text{ MB/min}$. In Erlang, process mailboxes consume RAM until the Linux kernel OOM killer abruptly terminates the VM.
  • Naive Buffer Drops $\to$ Catastrophic Frame Corruption: If buffers drop data naively when full, time continuity is severed. In ADS-B, an extended squitter frame spans $120\text{ }\mu\text{s}$ (240 samples at 2.0 MSPS). Dropping chunks at arbitrary boundaries fractures preambles, destroys matched filter phase coherence, and corrupts symbol timing loops (e.g. Gardner detectors).

2. GenStage Mechanics: Pull-Based Demand Contracts

To prevent unbounded mailbox growth while guaranteeing bounded latency, SdrScout employs GenStage. Rather than producers pushing data blindly downstream, GenStage inverts the control flow into a pull-based demand contract.

In a GenStage specification:

  • Producer: Source of events. It holds an internal demand counter state.demand. It is strictly forbidden from emitting events unless state.demand > 0.
  • Consumer: Sink of events. It dictates how many events it is ready to process by issuing demand tokens upstream.
  • ProducerConsumer: Intermediary filter or transformer that acts as a consumer to upstream stages and a producer to downstream stages.

Let us inspect the demand fulfillment loop inside lib/sdr_scout/pipeline/producer.ex: 

defmodule SdrScout.Pipeline.Producer do
  use GenStage

  @impl true
  def handle_demand(incoming_demand, state) do
    new_demand = state.demand + incoming_demand
    dispatch(%{state | demand: new_demand})
  end

  # Benchmark mode: greedily take up to demand chunks
  defp dispatch(%{chunks: chunks, demand: demand, mode: :benchmark} = state) when chunks != [] and demand > 0 do
    {to_emit, remaining} = Enum.split(chunks, demand)
    emitted_count = length(to_emit)

    new_state =
      %{state | chunks: remaining, demand: demand - emitted_count}
      |> maybe_reply_drain_waiters()

    {:noreply, to_emit, new_state}
  end

  defp dispatch(%{demand: demand} = state) when demand <= 0 do
    {:noreply, [], state}
  end
end

Notice how backpressure is enforced: if downstream DetectorConsumer is busy executing AVX2/NEON SIMD vector operations in Zig, it does not issue demand. The Producer's demand counter remains 0, and dispatch/1 returns {:noreply, [], state} without emitting any chunks.

3. Tuning the Window: The max_demand: 4, min_demand: 1 Contract

In lib/sdr_scout/pipeline/detector_consumer.ex, the consumer subscribes to the producer with precise demand parameters: 

@impl true
def init(opts) do
  producer = Keyword.fetch!(opts, :producer)
  ctx = Dsp.new_context()

  state = %{ctx: ctx, airspace: airspace, collector: collector}

  {:consumer, state, subscribe_to: [{producer, max_demand: 4, min_demand: 1}]}
end

Why exactly max_demand: 4 and min_demand: 1? Why not max_demand: 1 or max_demand: 100?

A. Bounding In-Flight Memory ($M_{\text{inflight}}$)

The parameter max_demand: 4 sets a strict upper bound on unconsumed data buffered between the producer and the consumer. Since each chunk is 64 KB:

$$M_{\text{inflight\_max}} = \text{max\_demand} \times S_{\text{chunk}} = 4 \times 65{,}536\text{ bytes} = 262{,}144\text{ bytes} = 256\text{ KiB}$$

256 KiB fits comfortably inside modern CPU L2/L3 caches (modern x86 L2 cache is typically 512 KB to 1 MB per core; Apple Silicon M-series L2 is 4 MB to 16 MB). By capping unconsumed chunks to 256 KiB, chunks remain in CPU cache hierarchy without evicting active working sets to main RAM!

B. Eliminating Pipeline Bubbles via min_demand: 1

If we had set max_demand: 1, min_demand: 0 (a stop-and-wait protocol):

  1. Consumer asks for 1 chunk.
  2. Producer sends 1 chunk (IPC latency $\tau_{\text{ipc}}$).
  3. Consumer processes chunk (DSP computation time $\tau_{\text{dsp}}$).
  4. Consumer asks for next chunk (IPC latency $\tau_{\text{ipc}}$).

The CPU core executing DSP math sits completely idle for $2 \times \tau_{\text{ipc}}$ between every chunk! This idle window is known as a pipeline bubble.

With max_demand: 4, min_demand: 1, GenStage uses an automatic replenishment watermark:

$$\Delta D = \text{max\_demand} - \text{min\_demand} = 4 - 1 = 3$$
  1. Upon initialization, the consumer immediately asks for 4 chunks.
  2. The producer delivers all 4 chunks. The consumer begins crunching Chunk 1.
  3. As the consumer finishes Chunk 3 (having processed $\Delta D = 3$ chunks), GenStage automatically dispatches a new demand request for 3 additional chunks in the background.
  4. While the consumer is processing Chunk 4, the producer receives the demand and delivers Chunks 5, 6, and 7 into the consumer's mailbox.
  5. When the consumer finishes Chunk 4, Chunk 5 is already waiting in the mailbox. Pipeline starvation is mathematically eliminated.

4. Zero-Copy Flow Across BEAM Mailboxes

A common critique of actor-model systems for high-performance computing is the cost of inter-process message passing. In classic actor runtimes, sending a message between processes requires serializing and deep-copying memory from the sender's heap to the receiver's heap.

In the BEAM, binary storage is split into two distinct tiers:

Binary Type Size Threshold Allocation Arena Mailbox Transfer Cost
Heap Binary $\le 64\text{ bytes}$ Process-private heap Full deep copy of byte payload
Refc Binary (Reference-Counted) $> 64\text{ bytes}$ Shared global off-heap memory Zero payload copy; copies 24-byte ProcBin pointer

Because each SDR chunk in SdrScout is $65{,}536\text{ bytes} \gg 64\text{ bytes}$, it is allocated as a Refc binary. When Producer sends to_emit chunks to DetectorConsumer: 

# Inside the BEAM:
# Only the 24-byte ProcBin descriptor is copied into DetectorConsumer's heap!
{:events, [refc_bin_1, refc_bin_2, refc_bin_3]}

The 64 KB radio buffer remains static in off-heap memory. Its atomic reference counter is incremented by 1.

When DetectorConsumer.handle_events/3 calls Zigler: 

# DetectorConsumer.ex
for chunk <- chunks do
  frames = Dsp.process_chunk(state.ctx, chunk)
  ...
end

ERTS passes the memory pointer from the ProcBin directly to the Zig NIF as a native slice: 

// dsp.ex (~Z native Zig code)
pub fn process_chunk(res: DspContext, chunk: []const u8) beam.term {
    // chunk.ptr points directly to the 64 KB off-heap buffer in RAM!
    // chunk.len is 65536.
    // Zero allocations. Zero memory copies.
}

The raw radio bytes flow from SDR hardware DMA buffers directly into the CPU's AVX2/NEON SIMD vector registers without a single memcpy operation.

5. Deterministic Drain vs. Realtime Streaming

In production SDR systems, testing and benchmarking streaming pipelines is notoriously difficult because developers often resort to flaky Process.sleep(...) statements to "wait for data to process".

SdrScout solves this with two explicit operational modes coordinated via lib/sdr_scout/pipeline.ex:

A. Realtime Paced Mode (Production Radio Reception)

In :realtime mode, the producer simulates or ingests hardware clocking. It releases 1 chunk every $T_{\text{chunk}} = 16.384\text{ ms}$: 

@chunk_interval_ms div(@chunk_size * 1000, @bytes_per_second) # 16 ms

defp dispatch(%{chunks: [chunk | rest], demand: demand, mode: :realtime, timer_active: false} = state) do
  Process.send_after(self(), :tick, @chunk_interval_ms)
  new_state = %{state | chunks: rest, demand: demand - 1, timer_active: true}
  {:noreply, [chunk], new_state}
end

B. Deterministic Drain Mode (Microbenchmarks & Unit Tests)

In :benchmark mode, we process datasets at maximum CPU throughput (often >100 MSPS) with zero sleep calls. To know exactly when the DSP pipeline has processed the final sample, Pipeline.drain/2 implements a two-phase barrier synchronization: 

# lib/sdr_scout/pipeline.ex
@impl true
def handle_call({:drain, timeout}, _from, state) do
  with :ok <- Producer.drain(state.producer, timeout),
       :ok <- DetectorConsumer.sync(state.consumer, timeout) do
    {:reply, :ok, state}
  else
    error -> {:reply, error, state}
  end
end
  1. Phase 1: Producer.drain/2: The producer receives :await_drain. If chunks remain in its queue, it stores the caller in state.drain_waiters. The moment the final chunk is emitted in response to demand, it replies :ok.
  2. Phase 2: DetectorConsumer.sync/2: The consumer receives :sync via GenStage.call/3. Because Erlang mailboxes strictly preserve FIFO ordering, the :sync message sits behind all preceding {:events, chunks} batches. When handle_call(:sync, ...) executes, every single prior I/Q chunk is guaranteed to have finished native Zig SIMD detection!

6. Architectural Showdown: GenStage vs. GNU Radio Flow Control

To appreciate why BEAM actor backpressure is uniquely suited for multi-channel SDR systems, let us compare it directly to GNU Radio's flow control architecture.

GNU Radio's Circular Buffer (vm_circbuf)

In GNU Radio (C++), each signal processing block runs in its own dedicated POSIX OS thread (pthread). Data flows through circular ring buffers connecting upstream block outputs to downstream block inputs.

To allow blocks to read contiguous memory without checking for buffer wrap-around, GNU Radio uses an operating system memory management trick: double-mapped virtual memory. It uses mmap or shm_open to map the same physical memory buffer into two contiguous virtual address regions:

$$\text{Virtual Range A: } [0, S_{\text{buf}}) \longrightarrow \text{Physical RAM Buffer}$$ $$\text{Virtual Range B: } [S_{\text{buf}}, 2S_{\text{buf}}) \longrightarrow \text{Same Physical RAM Buffer}$$

While this makes DSP loop pointer arithmetic fast, its flow control relies on POSIX synchronization:

  • When an upstream block's output buffer is full, its pthread blocks on a POSIX condition variable (pthread_cond_wait).
  • When a downstream block's input buffer is empty, its pthread blocks waiting for signal wakeups.
  • If 50 blocks exist in a flowgraph, 50 OS threads contend for CPU cores, causing frequent OS kernel context switches, cache line invalidations, and TLB shootdowns.

Checking Your Mastery

1. In SdrScout's DetectorConsumer, under what exact conditions does GenStage emit new demand upstream to the Producer?
  • Only after all 4 chunks are processed and consumer mailbox is completely empty.
  • Continuously on every clock cycle regardless of pending chunks or mailbox load.
  • As soon as 3 chunks have been processed, replenishing pending demand back to 4.
  • Whenever the OS kernel issues a SIGIO interrupt indicating full socket buffers.
Correct! In GenStage, when unfulfilled demand drops to min_demand (meaning max_demand - min_demand = 4 - 1 = 3 events have been processed), GenStage automatically issues a demand of 3 events upstream. This concurrent replenishment ensures the producer delivers the next batch while the consumer finishes the 4th chunk, eliminating pipeline starvation bubbles.
2. Why does passing a 64 KB I/Q chunk from Producer to DetectorConsumer avoid BEAM GC pauses?
  • The BEAM compiler rewrites the pipeline into an inlined C for-loop during compilation.
  • Binaries over 64 bytes are reference-counted off-heap, copying only a 24-byte pointer.
  • Erlang processes share identical OS thread stacks and bypass heap isolation entirely.
  • The operating system maps the binary directly into CPU L1 cache using hardware DMA.
Correct! In the BEAM runtime, binaries strictly larger than 64 bytes are allocated off-heap as reference-counted (refc) binaries. Passing a 64 KB chunk across an actor mailbox copies only a lightweight 24-byte ProcBin pointer descriptor onto the receiver process heap. The 64 KB payload stays in shared memory, incurring zero memory copy overhead and zero GC churn.
3. How does GenStage flow control differ fundamentally from GNU Radio's buffer management?
  • GenStage relies on hardware interrupts, whereas GNU Radio uses userspace green threads.
  • GenStage drops packets non-deterministically, while GNU Radio guarantees zero frame drops.
  • GenStage requires double virtual memory page mapping, whereas GNU Radio uses actor queues.
  • GenStage uses reactive message demand tokens, while GNU Radio blocks POSIX threads on ring buffers.
Correct! GNU Radio blocks dedicated OS pthreads using POSIX mutexes and condition variables when its double-mapped circular buffers are full or empty. GenStage relies on asynchronous reactive demand messaging, where downstream consumers explicitly pull discrete batches on BEAM user-space schedulers without blocking OS kernel threads.
