Lesson 0022 Systems & DSP Architecture Reading time: 15 minutes

Zero-Copy IPC & Circular Buffer Architectures: Page-Table Tricks vs. Erlang Refc Memory

In high-throughput Software-Defined Radio (SDR) engineering, memory bandwidth and cache locality dominate system performance. When sampling an RF spectrum at rates from $2.4\ \text{MSPS}$ (a modest RTL-SDR) up to $100\ \text{MSPS}$ (a dual-channel Ettus USRP X310 over 10-Gigabit Ethernet), raw complex baseband I/Q data arrives at rates between $4.8\ \text{MB/s}$ and $800\ \text{MB/s}$.

If your software pipeline copies each sample multiple times between kernel space, inter-process communication (IPC) queues, actor message mailboxes, and DSP compute kernels, memory bus contention quickly saturates the CPU memory controllers, induces cache eviction storms, and causes packet drops.

This lesson dissects the systems engineering mechanics of circular streaming buffers. We will contrast the classical GNU Radio double-mmap virtual memory trick (used in C++ flowgraphs) against the Erlang BEAM reference-counted binary model paired with native Zig tail buffers (used in SdrScout), examining page tables, MMU hardware translation, SIMD vector loads, and CPU cache-line alignment.

1. The Streaming Buffer Dilemma in Real-Time DSP

Why can't an SDR pipeline simply divide incoming sample streams into isolated, independent blocks and process them independently? The answer lies in the mathematical formulation of core DSP primitives:

A. Finite Impulse Response (FIR) Filtering

A discrete-time causal FIR filter computes output $y[n]$ as the linear convolution of input sequence $x[n]$ with an $M$-tap filter impulse response $h[k]$:

$$y[n] = (x * h)[n] = \sum_{k=0}^{M-1} h[k] \, x[n - k]$$

Notice the index term $x[n - k]$. To compute the very first output sample $y[0]$ of a freshly arrived buffer, the algorithm requires $x[-1], x[-2], \dots, x[-(M-1)]$—the final $M-1$ history samples from the previous buffer. Without contiguous access to these historical samples, convolution breaks across chunk boundaries.

B. Matched Filtering and Preamble Correlation

In digital communications and radar (e.g., Mode-S ADS-B preambles, FT8 synchronization sequences, or Barker codes), a receiver continuously evaluates the cross-correlation $R_{xp}[n]$ between incoming baseband samples $x[n]$ and a known reference pattern $p[k]$ of length $L$:

$$R_{xp}[n] = \sum_{k=0}^{L-1} p[k] \, x[n + k]$$

If an RF burst begins near the tail of chunk $N$ (for instance, at sample index $N_{\text{chunk}} - 10$), its remaining samples reside in chunk $N+1$. An isolated per-chunk processor will fail to detect the preamble because the pulse pattern is sliced in two.

C. Fast Fourier Transforms (FFT) and Overlap-Save

In polyphase channelizers and frequency-domain filtering, circular convolution via the Discrete Fourier Transform (DFT) is converted to linear convolution using the Overlap-Save or Overlap-Add algorithms. An $N_{\text{FFT}}$-point FFT requires an overlap of $M-1$ samples between successive blocks to discard time-aliased edge samples:

$$L_{\text{valid}} = N_{\text{FFT}} - M + 1$$

Every one of these fundamental DSP operations imposes the same strict hardware requirement: the vector compute engine must be supplied with a physically contiguous slice of memory containing the historical overlap followed immediately by the new samples.

2. Traditional Ring Buffers and the SIMD Vectorization Breakage

The classic computer science solution for streaming data is a FIFO circular ring buffer. A fixed-size array of length $N$ is accessed via modulo pointer arithmetic: 

sample = ring_buffer[index % N];

When $N$ is constrained to a power of two ($N = 2^k$), the expensive integer division instruction (div / idiv taking 12–25 CPU cycles) is replaced with a single-cycle bitwise AND mask: 

sample = ring_buffer[index & (N - 1)];

While masking is fast for scalar loops, it completely breaks down when modern vector processing instructions (AVX2, AVX-512, ARM NEON, or Zig @Vector) are introduced.

The SIMD Boundary Wall

An AVX2 vector load instruction (e.g., vmovups or _mm256_loadu_ps) reads 256 bits (32 contiguous bytes, or 8 single-precision floats) in a single clock cycle. It expects those 32 bytes to reside sequentially in the virtual address space.

If your read pointer sits at index $N - 4$ of an $N$-element buffer, a contiguous 8-float load requires elements:

[ x[N-4], x[N-3], x[N-2], x[N-1], x[N], x[N+1], x[N+2], x[N+3] ]

In a normal ring buffer, memory past $x[N-1]$ either belongs to another heap variable or is completely unmapped! If unmapped, the CPU triggers a Page Fault (SIGSEGV). If mapped to other memory, the CPU silently ingests garbage data into the DSP pipeline.

Engineers attempting to vectorise traditional ring buffers face three unsatisfactory workarounds:

  • SIMD Gather Instructions (_mm256_i32gather_ps): The CPU fetches each element using independent address translations. Gather instructions have high latency (12–20 cycles) and consume memory controller bandwidth, erasing SIMD speedups.
  • Scalar Loop Fallbacks: Splitting the loop into three sections: a vectorized prefix, a scalar boundary-wrap handler, and a vectorized suffix. This bloats code size, generates branch misprediction penalties, and complicates filter tap pipelines.
  • Intermediate Buffer Copying: Copying the wrap-around data into a linear temporary scratchpad before computing. This burns precious memory bandwidth on redundant memory writes.

3. The GNU Radio `vm_circbuf` Double-mmap Trick

GNU Radio solved this problem at the operating system and silicon level with an ingenious virtual memory architecture known as vm_circbuf.

Instead of performing modulo arithmetic in software, vm_circbuf offloads the circular wrap to the CPU's hardware Memory Management Unit (MMU) and page tables.

How Hardware Page Tables Work

Modern CPUs execute code using virtual addresses. The MMU translates every virtual address into a physical address using a hierarchy of multi-level page tables (PML4/PML5 on x86-64). The operating system controls the translation mappings by populating Page Table Entries (PTEs).

Crucially, multiple distinct virtual addresses can point to the exact same physical memory frame.

The Step-by-Step OS Implementation

To create a hardware-wrapped circular buffer of size $B$ (where $B$ is an integer multiple of the OS page size, typically $4096$ bytes), GNU Radio executes the following POSIX system call sequence:

  1. Create an anonymous shared memory file descriptor: 
    int fd = memfd_create("circbuf", MFD_CLOEXEC);
// or on older POSIX systems:
// int fd = shm_open("/circbuf_123", O_RDWR | O_CREAT | O_EXCL, 0600);
ftruncate(fd, B);
    This allocates physical backing store for exactly $B$ bytes in kernel shared memory.
  2. Reserve an unbroken contiguous virtual address space of size $2B$: 
    void *addr = mmap(NULL, 2 * B, PROT_NONE, MAP_ANONYMOUS | MAP_PRIVATE, -1, 0);
    The process obtains a continuous virtual window from address $A$ to $A + 2B$ without allocating physical RAM (PROT_NONE).
  3. Map the physical buffer into the first half $[A, A + B)$: 
    mmap(addr, B, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_FIXED, fd, 0);
  4. Map the exact same physical buffer into the second half $[A + B, A + 2B)$: 
    mmap((char *)addr + B, B, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_FIXED, fd, 0);
  5. Close the file descriptor: 
    close(fd);
    The mapping remains valid until unmapped.

The Architectural Payoff

Consider what happens when a DSP algorithm running AVX2 instructions processes data near the end of the buffer:

  • The read pointer is at index $B - 4$.
  • The SIMD kernel issues a 32-byte load instruction: _mm256_loadu_ps((float*)(addr + B - 4)).
  • The first 4 floats (16 bytes) are read from the tail of Virtual Mirror 1 ($[B-4 .. B-1]$).
  • The remaining 4 floats (16 bytes) are read from the head of Virtual Mirror 2 ($[B .. B+3]$).
  • Because the MMU maps virtual page $[A + B .. A + B + 4096]$ to the exact same physical frame as $[A .. A + 4096]$, the hardware MMU fetches the first 4 samples of the physical buffer automatically.

There are zero branch instructions, zero modulo operations, zero temporary buffer copies, and zero scalar loops. As long as no single SIMD kernel access spans more than $B$ contiguous bytes, the pointer can advance linearly through the buffer indefinitely!

4. The Architectural Tradeoff on the BEAM

If the double-mmap trick is so elegant, why doesn't every high-performance language—including Elixir and the Erlang VM (BEAM)—use it for all I/Q streaming buffers?

To understand this, we must inspect the Erlang Run-Time System (ERTS) memory model:

Binary Type Size Threshold Allocation Location Lifecycle & GC Mechanics
Heap Binary $\le 64$ bytes Private process heap Copied between processes on message passing; collected during generational process GC.
Refc (Reference-Counted) Binary $> 64$ bytes Global off-heap ERTS slab memory Shared globally across all processes; processes only pass a 24-byte ProcBin pointer. Reclaimed when atomic refcount drops to 0.

Why Double-mmap Cannot Safely Wrap BEAM Process Heaps

Attempting to apply double-mmap directly to BEAM managed memory creates insurmountable architectural collisions:

  1. Slab Allocator Incompatibility: ERTS manages off-heap memory through custom multicarrier allocators (erts_mseg and sys_alloc). Arbitrary Refc binaries are sub-allocated inside shared memory supercarriers. They are not guaranteed to begin on an OS $4096$-byte page boundary, nor are their lengths page-aligned.
  2. Catastrophic Page Table Clashing: Calling mmap with MAP_FIXED over memory belonging to the BEAM process heap would clobber Erlang memory tags, corrupt the Cheney copying garbage collector pointers, and cause immediate VM panics.
  3. Violation of Immutability and Shared-Nothing Semantics: In OTP, Erlang terms are fundamentally immutable. A double-mmap buffer creates an aliased, mutable memory region where writing to address $V_2$ mutates address $V_1$. If this memory were exposed to Elixir processes, it would violate the referential transparency and actor isolation that makes the BEAM fault-tolerant.
  4. Virtual Memory Allocation Limits: Operating systems enforce limits on the number of distinct memory mappings per process (e.g., Linux vm.max_map_count, typically defaulting to 65,530). In an SDR cluster running thousands of concurrent channelizers or detector actors, creating two VMAs per channel would exhaust kernel descriptor tables.

5. The SdrScout Tail-Buffer Hybrid Architecture

In lib/sdr_scout/native/dsp.ex, SdrScout resolves this dilemma with a hybrid architecture:

  • Elixir / GenStage moves 64 KB Refc Binaries with zero copying.
  • Zig NIFs maintain a lightweight 480-byte persistent overlap buffer inside an Erlang Resource (beam.Resource).

How the Tail-Buffer Mechanics Work

Let's trace how SdrScout.Native.Dsp.process_chunk/2 operates:

  1. Zero-Copy Delivery: The RTL-SDR driver delivers raw bytes into an off-heap Refc binary. Elixir's GenStage pipeline routes the binary reference to the DSP worker. When calling into Zig, ERTS passes the raw memory address as a native Zig slice: 
    pub fn process_chunk(res: DspContext, chunk: []const u8) beam.term
    No memory allocation or data copying takes place to cross the language boundary.
  2. Linear Stitching: The NIF allocates a local stack/arena working buffer of size $\text{total\_bytes} = 480 + \text{chunk.len}$. It copies the 480 bytes stored from chunk $N-1$ into the head, followed by the 65,536 bytes of chunk $N$.
  3. Uninterrupted SIMD Processing: The native Zig code executes @Vector(16, f32) AVX2/NEON instructions across the entire 66,016-byte buffer in a tight linear loop. There are no boundary checks or branches inside the inner loop.
  4. Tail Preservation: Before returning, the NIF copies the final 480 bytes of chunk $N$ into the persistent DspContext.overlap_buf struct: 
    const save_start = total_bytes - 480;
@memcpy(ctx.overlap_buf[0..480], iq_buf[save_start..total_bytes]);
ctx.overlap_len = 480;

Quantitative Overhead Analysis

What is the cost of copying 480 bytes per chunk compared to page-table double-mmap?

$$\text{Memory Overhead} = \frac{480\ \text{bytes}}{65,536\ \text{bytes}} \approx 0.00732 = \mathbf{0.73\%}$$

On a modern x86-64 or ARM Cortex-A72 CPU, copying 480 bytes (less than eight 64-byte cache lines) using L1 cache prefetching takes approximately 12 to 18 nanoseconds.

In contrast, calling mmap and munmap incurs operating system kernel context switches, Translation Lookaside Buffer (TLB) shootdown inter-processor interrupts (IPIs), and page-table lock contention taking 2,000 to 5,000 nanoseconds.

The Engineering Verdict

For fixed chunk-based pipelines, copying a small sub-kilobyte tail buffer inside native memory is orders of magnitude faster and vastly more memory-safe than invoking OS virtual memory system calls, while completely maintaining BEAM crash isolation and actor supervision!

6. CPU Cache Lines, False Sharing, and Cache-Coherent DMA

Whether you design a page-table circular buffer or a tail-buffer pipeline, real-time performance at tens of megasamples per second requires strict alignment to the CPU's memory hierarchy.

A. 64-Byte Cache Line Granularity

CPUs do not read or write individual bytes from system DRAM; they access memory in 64-byte chunks called cache lines.

If an I/Q sample structure or circular buffer header is not aligned to a 64-byte boundary, a single SIMD vector instruction can span across two separate cache lines. This triggers a split-cache-line penalty, requiring two distinct L1 cache access cycles and stalling the execution pipeline.

B. False Sharing in SPSC Ring Buffers

In multi-threaded C/Rust pipelines or native lock-free queues connecting hardware drivers to processing threads, developers commonly use a Single-Producer Single-Consumer (SPSC) ring buffer.

An SPSC queue maintains two atomic tracking indices:

  • head (or write_ptr): Updated exclusively by the producer thread (e.g., USB DMA interrupt).
  • tail (or read_ptr): Updated exclusively by the consumer thread (e.g., DSP worker).

Consider this seemingly innocent struct declaration: 

// NAIVE LAYOUT: Triggers devastating false sharing!
struct SpscQueue {
    head: usize, // 8 bytes
    tail: usize, // 8 bytes
    // ...
};

Because both head and tail occupy adjacent 8-byte slots, they reside on the exact same 64-byte cache line!

Under the MESI (Modified, Exclusive, Shared, Invalid) hardware cache coherence protocol:

  1. Core 0 writes to head, marking the entire 64-byte cache line as Modified (M).
  2. Hardware bus snooping automatically forces Core 1's copy of that line into the Invalid (I) state.
  3. When Core 1 reads or updates tail, it suffers a full L1/L2 cache miss. It must issue a bus request to flush Core 0's cache line to L3 or DRAM.
  4. This cache line "ping-pongs" between cores across the interconnect on every single sample chunk, reducing queue throughput by up to 90%!

The solution is explicit 64-byte alignment and padding: 

pub const SpscQueue = struct {
    head: usize align(64),
    // Explicit padding guarantees tail occupies a separate cache line
    tail: usize align(64),
};

C. Cache-Coherent Direct Memory Access (DMA)

When hardware SDRs (e.g., RTL-SDR via USB 2.0/3.0, or USRP via PCIe/Gigabit Ethernet) capture radio samples, the onboard hardware DMA controller writes data directly into host physical RAM without CPU intervention.

Modern architectures maintain cache coherency via hardware interconnect snooping (PCIe Root Complex on x86, or CoreLink CCI/CCIX on ARM). However, if an SDR driver initiates DMA into an unaligned memory address:

  • The start or end of the DMA transfer shares a cache line with adjacent kernel or user variables.
  • If the CPU writes to an adjacent variable while the hardware DMA controller is simultaneously writing radio bytes to that same cache line, a cache-line tearing corruption occurs: either the CPU's write is discarded or incoming RF samples are permanently overwritten!

For this reason, high-speed SDR drivers always allocate page-aligned DMA ring buffers (using posix_memalign or Linux dma_alloc_coherent) to ensure clean separation at both the 64-byte cache line and 4096-byte MMU page levels.

  • The CPU hardware ring buffer unit wraps addresses when pointers exceed the L1 cache boundary.
  • The operating system dynamically allocates an extra 64-byte page whenever a vector register wraps.
Correct! In the double-mmap architecture, two contiguous virtual address windows $[A, A+B)$ and $[A+B, A+2B)$ point to the identical physical RAM pages in the MMU page table.   • Reference-counted binaries in Erlang are always constrained to a maximum size of 64 bytes total.
  • BEAM slabs are not page-aligned, and aliased mutable memory violates actor immutability invariants.

Correct! Erlang off-heap Refc binaries are managed by internal multi-carrier slab allocators and are not guaranteed to be page-aligned or page-sized. Furthermore, double-mmap creates an aliased, mutable memory region, which violates the immutability and actor isolation guarantees of the BEAM.
